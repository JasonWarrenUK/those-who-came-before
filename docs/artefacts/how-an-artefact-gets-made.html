Those Who Came Before
Engineering Notes · Generation Pipeline

How an Artefact Gets Made

Those Who Came Before is a game about an archaeologist whose mistakes compound into an unreliable narrative. For that to work, the things being misinterpreted have to be real: every artefact is a physical object generated from a seed, with a structure, materials, decoration and a ground truth the player never reads directly. These pages explain how that generator works, in the order the pipeline runs.

Written for developers who build software but haven't built procedural generation. No prior archaeology required; no prior game development either.

01 · Pipeline

Nine Stages, Three Cadences

Every artefact the player will ever touch has passed through nine stages, in order. The stages run at three different cadences, and knowing which cadence a stage runs at tells you most of what you need to know about it.

The spine

World Seed
  → Chronology & Culture Generation        (once per game)
    → Initial Corpus Generation             (once per game)
      → Bottom-Up Structural Grammar        (per artefact)
        → Normalisation + Plausibility      (per artefact)
          → Material Assignment             (per artefact)
            → Decorative Grammar            (per artefact)
              → Feature Extraction + Tags   (per artefact)
                → Description Generation    (per inspection)

The three cadences do different jobs. Stages 1–3 run once, at world creation: they produce the chronology, the cultures, the geology and a simulated century of scholarship for the player to inherit. Stages 4–8 run every time the world needs a new artefact: they build a physical object, dress it and score it against the tag vocabulary. Stage 9 runs every time the player inspects an artefact, because the player's beliefs and available registers shift between viewings; the same object can read differently on Tuesday than it did on Monday, and that is the game.

The one idea that organises everything

Structure comes first and meaning comes last. The grammar in stage 4 produces geometry with no idea what it's for; classification in stage 8 reads that geometry back and scores it against functional tags; the description in stage 9 hedges even those scores through registers and the player's interpretive lens. Nothing upstream ever branches on "make a sword". If you take one thing from these pages, take that: the pipeline is a one-way flow from physical fact to contested interpretation, and every stage boundary is a place where information is deliberately narrowed.

Visibility levels

Every property the pipeline produces sits at one of four visibility levels, and the level is part of the type system's contract rather than a rendering nicety.

LevelMeaningExamples
ObservableDirectly perceptible on inspectionComponent structure, decoration layers, material identity
InferableRecoverable by reasoning from observablesMaterial provenance, motif significance
OccludedGround truth the player must guess at, never readsChronology, culture profiles, true tag scores
Engine-internalNot a world fact at allThe seed, plausibility checking, corpus simulation

The interpretive lens (the game's core mechanic) operates on observable and inferable properties only. It can reorder, reframe and de-emphasise; it cannot reveal occluded properties and it cannot hide observable ones. That constraint is what keeps the unreliable-narrator premise honest: the player is misled by their own filtering, never by the engine lying about physics.

What exists today

The implementation restarted from scratch for launch and is being rebuilt against a 318-task MVP roadmap; 89 tasks were done at the time of writing. Milestone 1 (runtime, the full type system, the seeded PRNG, the developer workbench) is complete. Milestone 2 is the generation pipeline itself, at 49 of 101 tasks.

  • Stages 4–8 are shipped as pure TypeScript engine modules: grammar expansion, normalisation, plausibility, materials, decoration, feature extraction and classification, each with substantial test suites.
  • Stage 9 is partial. The observational register's templates and a minimal renderer exist; the full description engine (variant selection, register filtering, lens integration) is a later roadmap task.
  • Stages 1–3 are designed but not built. The engine currently runs against mock cultures and six fixture worlds. Page 09 covers what's coming.

02 · Foundations

Every Draw Is Accounted For

The entire game world unfolds from one seed string. Same seed, same world, same sequence of artefacts, on every machine, forever. That guarantee rests on a module about a hundred lines long, and on a discipline the rest of the engine has to keep.

The generator

The seed string is hashed by xmur3 into a stream of well-mixed 32-bit integers, which seed the four state words of a xoshiro128** generator. Each call advances the state and returns a float in [0, 1). There's a guard against the all-zero state (xoshiro is degenerate there; xmur3 makes it vanishingly unlikely, but a guard is cheaper than an incident) and that is essentially the whole module. Nothing exotic. The interesting part is what the rest of the codebase is obliged to do with it.

Determinism is injected, never ambient

No engine module ever calls Math.random(). Every generation function takes a prng: () => number parameter, and determinism flows entirely from that injection. The engine modules are pure TypeScript with no framework or browser dependencies; the design docs call this the engine boundary, and it's what makes the whole pipeline runnable in a test, a CLI sampler or a browser panel with identical output.

Draw ordering is part of the API

Here's the discipline that surprises people who haven't built seeded generation before: how many times a function draws from the PRNG is a contract, not an implementation detail. selectGrammarOption documents that it consumes exactly one draw per call regardless of how many options it weighs. If a refactor made it draw twice, every seed in existence would produce a different world, and every regression fixture would be lies. Consumers are entitled to rely on a fixed number of draws per selection; changing the draw count is a breaking change even when the function's return type is untouched.

The transferable lesson In seeded procgen, your PRNG call sequence is a serialisation format. Treat "how many draws, in what order" with the same care you'd treat a wire protocol, because that's what it is: the seed is the message and the draw sequence is the schema.

Weighted selection

One utility, weightedSelect, does nearly all the choosing in the pipeline. It takes candidates, a PRNG and a weight callback; the callback shape exists because callers weigh differently-shaped things (grammar options by effective weight, materials by a three-factor product). Two edge cases are handled deliberately: a zero-total weight table degrades to a uniform draw rather than crashing or silently picking the first item, and floating-point drift on the final subtraction falls through to the last candidate.

export function weightedSelect<T>(
  items: readonly T[],
  prng: () => number,
  getWeight: (item: T) => number,
): T

What the seed does and doesn't pin

The guarantee is phrased carefully: same seed means the same sequence of artefacts. Artefact N may depend on artefacts 1 through N−1 (associated finds, site reuse, material precedent), so the seed determines the unfolding, and no artefact is addressable in isolation. If you want artefact 500, you generate the 499 before it.

03 · Stage 4

The Grammar Doesn’t Know What a Sword Is

Stage 4 builds the physical object. It works bottom-up from geometric primitives, and it is forbidden, as a matter of design law, from ever branching by intent. The spec marks exactly one principle non-negotiable, and it's this one.

Why bottom-up

The obvious way to generate game items is top-down: pick "sword" from a table, then fill in sword-shaped details. The whole game premise dies if you do that. If the generator knows it made a sword, the classification is trivially recoverable and interpretation has nothing to do; the player's job of working out what a thing was only exists if the engine itself never decided. So the grammar produces structures (an elongated form with an edge, socketed to a cylindrical form) and classification happens downstream, by reading the geometry back like an archaeologist would. Ambiguity isn't sprinkled on top; it falls out of the fact that a long edged thing genuinely might be a weapon, a tool or a ritual object, because nothing anywhere says otherwise.

The vocabulary

Eight geometric primitives, each with its own parameter set: elongated, cylindrical, flat-broad, hollow-enclosed, ring-form, disc-form, bar-form, sheet-form. An elongated form has a length band, a cross-section, a taper, an edge count and a point; a hollow-enclosed form has a shape, wall thickness, an opening and a base. Components join through nine attachment types (inline, perpendicular, socketed, riveted, wrapped, lashed, hinged, threaded, friction-fit), and the attachments matter later: a hinged join is evidence of fine metalwork, and classification will read brooch anatomy off a pin bearing on a hoop.

<object>            ::= <component-group>+
<component-group>   ::= <primary-component> [<attachment> <component-group>]*
<primary-component> ::= <elongated> | <cylindrical> | <flat-broad>
                      | <hollow-enclosed> | <ring-form> | <disc-form>
                      | <bar-form> | <sheet-form>

The BNF's repetition operators are engine-owned: the data module supplies alternatives and weights only, and expandGrammar decides how many groups and how long the attachment chains run, bounded by the complexity budget below. Grammar rules live in a data file as plain objects; the engine looks them up by symbol. Four production rules cover the MVP.

Culture biases, never dictates

Cultures don't have allowed artefact types. They have tendencies, expressed as weight modifiers over grammar options. Selection works like this: start from the option's authored base weight, add each cultural modifier scaled by the culture's affinity for that material tag, multiply by phase influence, floor at 0.01.

weight = max(0.01,
  (baseWeight + Σ affinity(tag) × modifier)
  × Π (1 + (multiplier − 1) × phaseAttribute))

Two properties of this formula carry design weight. The 0.01 floor means nothing is ever impossible: a deeply pacifist culture occasionally produces a blade, because archaeology is like that (the comment in the source says exactly this). And phase influence is calibrated so a high attribute amplifies while a low attribute merely fails to amplify; "low metallurgy" never punishes an option below its base weight, matching the doc's framing that attributes increase probabilities rather than gate them.

A phase is a multi-attribute profile, one per culture per period: eight technology axes (metallurgy, ceramics, textiles, leather-working, stone, glass, wood, bone), plus economy, society and aesthetics blocks. A culture can be exceptional metalworkers with crude ceramics, and its artefacts will say so.

Complexity budgets and arrangement patterns

Uncontrolled repetition produces nonsense, so repetition is patterned. The culture's craftSpecialisation resolves to one of three tiers: simple cultures get 1–2 component groups and basic patterns (symmetric, linear); moderate get 2–3 groups and most patterns; sophisticated get 3–4 groups and all six, including nesting and branching. Six arrangement patterns constrain how a component repeats: symmetric pairs, radial spreads of 3–12, linear arrays, stacks, nests, branches. An accumulation checker validates the expanded tree against these constraints after the fact.

Portability, derived

Generated objects carry a portability band, from pocketable through team-lift to major-effort, and an inspection depth derived from physical dimensions: anything up to 30cm can be held and fully examined, up to 150cm examined in detail, beyond that observed in situ. These are mechanical facts about player handling. Hold that thought for page 07, because there's a rule about who is allowed to read them.

04 · Stage 5

Nonsense Is Rejected, Never Patched

The grammar is honest about geometry and ignorant of physics. Stage 5 flattens its tree into a normalised structure, then checks the result against physical plausibility rules. What happens on failure is the most opinionated engineering decision in the pipeline.

Normalisation

Grammar expansion yields a tree; downstream stages want a flat, standardised shape. NormalisedArtefact carries the component list (each with its primitive type, parameters, position along the primary axis and arrangement-group membership), the attachment list, derived dimensions, portability and inspection depth. The spec also makes normalisation the owner of allowedMaterialTags per component, derived from a physical compatibility table: an edged elongated form admits metal and stone; a hollow-enclosed form admits clay, metal, wood and stone. Physics supplies these constraints; the grammar never did. In the shipped code the field is honestly stubbed empty (its compatibility table is a scheduled task, 2GN.10, and the stub is labelled as such at the assignment site), and the convention downstream is that an empty list means "no constraint recorded yet" rather than "nothing fits".

The rule set

type PlausibilityRule =
  | { type: 'requires';  component: string; dependsOn: string }
  | { type: 'excludes';  component: string; excludes: string }
  | { type: 'ordering';  component: string; before?: string; after?: string }
  | { type: 'material-physics'; predicate: (a) => boolean; reason: string }
  | { type: 'ergonomic';        predicate: (a) => boolean; reason: string }

The rules encode things a craftsperson would never build: an edged form with nothing grippable attached, a long blade on a stubby grip, a heavy head lashed to a cord, a heavy component perched on a thin-walled vessel. Each predicate rule carries a human-readable reason, because a failed check is a diagnostic, and diagnostics that can't explain themselves are noise.

Fail loudly or don't fail at all

When plausibility fails, the pipeline re-expands from stage 4 and tries again, up to N attempts. Grammar expansion is cheap; re-rolling is the intended control flow. The interesting case is exhaustion. If all N attempts fail, the contract (assigned to a scheduled roadmap task; checkPlausibility is shipped, the retry orchestration around it comes with the pipeline assembler) is to throw a typed PlausibilityExhaustedError carrying the seed, the attempt count and the last failing rule set. Not to relax the rules. Not to emit a canned fallback artefact.

Why throwing is correct here Exhaustion means the grammar and the rule set disagree: a generator defect to surface, never a runtime condition to paper over. A relaxed rule set would break the pipeline guarantee that every artefact reaching the player passes every plausibility rule. A fallback artefact not derived from the grammar would break Simulation Honesty, the design pillar that says all player-facing content derives from the same underlying data. Both escape hatches are cheap to build and each quietly destroys an invariant the rest of the game leans on. The strongest case for a fallback is availability (a live game that throws is worse for the player than one that shows a slightly wrong pot); the project's answer is that the error is a development-time signal by construction, because determinism means any exhausting seed can be reproduced and fixed before release.

The guarantee it buys

This stage is why the pipeline can promise structural coherence unconditionally: no artefact that fails a plausibility rule ever reaches the player, and the promise holds vacuously through exhaustion because in that case nothing reaches the player. Guarantees phrased to hold vacuously survive edge cases; guarantees phrased as "we always produce something valid" quietly become "we usually do".

05 · Stage 6

Fake Relics Obey Real Geology

Materials are assigned per component, and the assignment is where the world outside the object first presses in: what the region's geology offers, what the culture prefers, what its technology can work at this point in its history.

The catalogue

Sixteen materials, each a definition with tags, availability data and physical properties: bronze, iron, gold, silver, obsidian, flint, granite, jade, oak, ash, bone, antler, fired clay, glass, linen, leather. Tags group them (metal, stone, wood and so on) so that component compatibility can be expressed against kinds while selection lands on specifics.

Selection: two filters, a ladder, one product

  1. Compatibility filter. Keep materials whose tags intersect the component's allowedMaterialTags; an empty constraint list admits everything.
  2. Availability filter. Keep materials obtainable in this geology, locally or via a trade flow.
  3. Fallback ladder. If availability empties the pool, fall back to the compatible set; if that's empty, the full catalogue. The function never hands weightedSelect an empty list, so it never throws on a populated catalogue.
  4. Weighted draw. Survivors are weighted by the product culturalAffinity × phaseTechnology × scarcity.

Availability is a five-rung ladder per material per region: abundant, available, scarce, trade-only, absent. A trade-only material is rescued by a matching MaterialFlow in an active relationship window; an absent one is excluded outright. Scarcity then weights the survivors: 1.0, 0.6, 0.25, 0.15 down the rungs. A scarce material still appears, just rarely, and a trade material arrives at the doc's "present but uncommon" level.

Weights are ratios, and the tests know it No document anywhere specifies "12% bronze". The spec states priorities directionally and explicitly disclaims quota readings; the numbers above are authored, marked MVP-provisional. What stops a typo silently reshaping the world is a calibration test suite that pins the distribution: per-region tag shares, splits within a tag (how metal divides into bronze, iron, gold, silver) and a provenance mix sensitive specifically to the trade-only rung. Before that suite existed, the distribution tests were bare directional inequalities that would pass for any descending set of four numbers; nothing could tell a deliberate recalibration from a slip. That gap, and the fix, are recorded in the doc itself.

Provenance: the engine remembers, the player infers

Each assignment carries provenance metadata: local, regional or trade sourcing, a likely origin region, a trade-path reference. All of it is hidden. The player sees a copper object from a culture with no copper deposits and has to construct the explanation themselves; trade, migration, conquest, a stolen trophy and a misattributed culture are all live hypotheses, and the relationship data upstream genuinely supports several of them. The engine holds the answer and never volunteers it.

Physical properties feed the next stage

Each material definition carries seven authored physical axes plus a keyed reactivity object: hardness on the real Mohs scale, fragility, rigidity, grain fineness, porosity, combustibility and formability (this last one assessed at the material's working state rather than its finished state, the one axis on that convention, an inconsistency the docs name rather than hide). These axes exist because decoration needs them: substrate prerequisites and execution difficulty both resolve against named physical facts. An earlier model with a vague workable boolean was retired for conflating brittleness, pliability and grain coarseness; the replacement lets each check name the fact it actually depends on.

Honest scaffolding

Milestone 2 runs this stage against mock world fixtures, and the module JSDoc is blunt about the consequences: there's no culture-to-region mapping yet, so availability answers "obtainable anywhere in this geology" rather than gating on the artefact's eventual findspot region, and the trade-path id is a synthesised string because relationships don't carry stable ids yet. Each shortcut names the roadmap task that retires it. Provisional code that documents its own provisionality is the pattern to steal here; the alternative is scaffolding that quietly becomes load-bearing.

06 · Stage 7

Every Layer Is an Act of Craft

After structure and materials, a second grammar runs over the artefact, treating each component as a potential canvas. Decoration isn't cosmetic in this game: it feeds the same classification as structure, it carries the strongest cultural fingerprints and it's where the pipeline's best bug stories live.

Sixteen techniques, three families

The decorative BNF has three categories: surface treatments (polish, patina, roughening, scoring, engraving, relief, painting, glaze), applied elements (inlay, overlay, studs, wire-wrapping, gilding) and textile elements (wrapping, tassels, beading). Each technique declares a substrate prerequisite, and the prerequisites resolve against the material property axes from stage 6 rather than vibes:

  • Engraving requires a material that can hold an incised line; soft precious metals qualify via chasing and repoussé despite not being structurally hard. Workability, not raw hardness.
  • Relief requires formability ≥ 3: the material must take a raised form at all. The earlier rigidity proxy wrongly admitted obsidian and flint (worked only by conchoidal fracture) and wrongly excluded leather (tooled or wet-moulded into relief for millennia).
  • Gilding gates on rigidity. The spec once said "you don't gild wood", and that sentence has been removed as factually wrong: gilded wood over gesso is the commonest gilding in the historical record. The doc keeps the correction inline, dated, with the reasoning.

Technique choice and imagery are independent signals

A culture's preference for techniques (techniqueAffinities) is deliberately separate from its motif vocabulary and from its material affinities. A culture can engrave beasts, engrave without beasts, depict beasts without engraving or do neither; those four combinations only exist if the two signals vary independently, so the type system keeps them apart. On top of affinity sits a one-directional material-access gate: a culture with no suitable material in plentiful, favoured supply has the technique suppressed however much it "likes" it, but favouring a suitable material never forces the technique. You can't engrave what you cannot obtain; owning bronze doesn't oblige you to decorate it.

The wire-wrapping defect The gate originally checked only a technique's substrate. Wire-wrapping's substrate is the grippable form it wraps, which is fine; the metal wire is a material the technique introduces, and that side went unchecked. Result, found by measurement rather than review: metal-free cultures produced more metal wirework than anywhere else in the world. The gate now checks both what a technique sits on and what it brings with it. Semantic bugs like this pass every type check and every unit test written from the same mental model; the sampling harness that catches them is on page 10.

How much, versus how well

The spec described a 2×2 of craft skill against decorative emphasis, controlling recursion depth. Measured against the real pipeline, its two middle corners ("technically refined but sparse", "abundant but simple") proved unsatisfiable by any single volume scalar, because they differ in kind rather than magnitude. The shipped design splits the axes into two mechanisms. Volume (layers per component) reads the culture's decorative emphasis alone. Grade (a 0–1 execution quality per layer) reads craft specialisation scaled by the technique's own difficulty; polish and scoring sit at the easy end, inlay and gilding at the hard end. Craft keeps one legitimate indirect effect on volume: high-craft cultures build more complex objects, and more parts means more canvases.

Grades get a second pass once materials are known, because execution difficulty is material-sensitive: engraving iron and engraving gold no longer score identically. Classification later reads mean decorative grade as a quality signal independent of quantity, which is what lets a sparse, superb object outrank a busy, clumsy one.

Motifs, borrowed and otherwise

Motif-carrying layers draw from the producing culture's motif vocabulary, weighted 1, plus motifs borrowed through any cultural-exchange relationship active in the production year, weighted by that window's exchange intensity. Introduced materials for techniques like inlay are constrained to per-technique tag sets and weighted by the same affinity × technology × scarcity product as structural assignment. This is where interpretive ambiguity gets manufactured wholesale: an artefact bearing Culture B's motifs might be B's work, or A's work under heavy exchange, and the sequence of layers (base engraving in one vocabulary, later inlay in another) hints at reworking without any flag saying so. The system produces layers; noticing is the player's job.

Deliberate gaps

Layers currently ship flat: sublayers is always empty, and decoration-on-decoration is a scheduled task rather than an accident. Substrate enforcement strips candidate layers whose component's actual material fails the prerequisite, except for the three form-substrate techniques (wire-wrapping, wrapping, beading), which pass through unstripped because nothing in the pipeline can yet answer a geometry question about a component; stripping on a check that cannot run would delete three techniques from every artefact on no evidence. The module JSDoc lists each gap, its owner and its reasoning. That's the house style: a gap you can cite beats a gap you have to discover.

07 · Stage 8

Tags Are Evidence Tallies

Stage 8 is where the pipeline reads its own output back. A single extraction pass turns the finished object into a feature set; 44 scoring rules turn features into tag scores. The scores are the game's occluded ground truth: the player's claims are eventually judged against them, and the player never sees them.

Extraction: one pass, one value per question

extractFeatures runs once across components, attachments and decorative layers together, and it's pure and PRNG-free: same artefact in, same features out. The awkward part of feature extraction is collisions. An artefact can have three edged components; which one is "the blade"? Every multi-component collision resolves to one value through a documented collapse policy: blade fields read from the dominant edged component (longest, earliest position on ties) so length band and profile never describe different blades; container fields read from the dominant container (largest hollow-enclosed, falling back to longest cylindrical) so a bowl with a socketed ferrule reads the bowl's opening and base; categorical fields like perforation collapse to the most classificatorily loaded value present, with the priority order pinned in comments.

Some features have no single grammar signal and are derived from interviewed anatomy rules instead. An impact surface is an untapered bar end or a thick disc (hammer, pestle, mace head). A fastening mechanism is brooch anatomy (a sharp, edgeless pin bearing on a hoop) or any hinged join, gated to body scale. Wearability is a ring form or a suspension perforation, gated the same way, because a hinged chest lid is not a dress fastener and nobody wears a perforated slab. The presence flags deliberately refuse the module's own graceful-degradation contract: unrecognised signals leave them false, so degradation can never fabricate a pin.

A boundary with a test on it No classification rule may read portability or inspectionDepth. Both derive from the same dimensions as the physical massBand and sizeBand, but they are mechanical facts about player handling, and letting classification consume them would smuggle game mechanics into world semantics. Rules read the physical bands instead, and a boundary guard test fails the suite if any rule ever touches the mechanical pair. Enforcing an architectural boundary with a test costs ten lines and survives every future contributor's good intentions.

Scoring: a fold you can reason about

classifyArtefact runs all 44 rules and folds every matching rule's tag weights into one map by plain unbounded sum, iterated in canonical vocabulary order. No normalisation, no softmax, no cap. The docs are explicit about what the numbers mean: evidence tallies, never confidences. Consumers compare by rank and margin and read absent tags as zero. An engraved bronze blade scores on weapon, ritual, ceremonial and elite simultaneously, and the system leaves the tension unresolved because resolving it is the player's entire job.

Two kinds of tag, and why the split earns its keep

The vocabulary splits by scoring basis. Absolute tags (weapon, tool, container, fastener, ornament, domestic, agricultural, maritime, trade-good, currency) are reachable from physical affordances alone and score against fixed thresholds. Relative tags (personal, communal, elite, utilitarian, ceremonial, everyday, military, artisanal, ritual, votive, funerary) assert something about an artefact's standing among its own culture's output, and they score against baselines sampled per culture-phase: the engine generates 400 artefacts through stages 4–7 for that culture-phase, builds percentile ladders over the sampled features and scores the real artefact against those. There's no bootstrap circularity because nothing upstream of classification reads a tag.

The split was forced by a measured failure. Under absolute thresholds, the applied-element rule fired on 4.3% of artefacts from an austere culture and 48.1% from a decorative one, an order of magnitude of phase sensitivity; "elite" had quietly come to mean "unusually decorated in absolute terms", so a decorative culture read as composed almost entirely of elites. The design pillar being violated has a name (Simulation Honesty), and the fix follows the tag's semantics: elite means unusually rich for this culture, so the threshold must come from this culture's own distribution.

Calibration is measured, never transcribed

The spec's illustrative thresholds (decorativeComplexity > 2 and friends) were authored before any decoration pipeline existed. Once one did, sampling 1200 real artefacts showed those thresholds firing on 87–99% of output; under a plain-sum fold, a rule that fires on nearly everything adds a constant to every score and discriminates nothing. The shipped thresholds are pinned to measured percentiles of real output, and the doc carries the distribution table. A later re-measurement found the original sample itself was skewed: the mock geology modelled only 4 of 16 materials, so the other twelve passed an "unmodelled means obtainable" lenience at full weight and silver came out the world's second commonest material. Re-sampling 7200 artefacts across six fully modelled fixture worlds corrected the material mix and, usefully, proved the elite inflation (steady at ~90% presence in every world) had never been material-driven in the first place.

Even the migration to percentiles carries a recorded subtlety: sampled features are coarse integers with heavy tie-mass, and the comparison is ≥, so a p75 threshold landing on a tie point admits the whole tie and fires at nearly double the implied rate. Each migrated rule records the realised fire rate it was checked against rather than trusting the rung's name. Of the rules awarding relative tags (35 of the 44, per the pinned split), only nine had numeric conditions a percentile could replace, and those are migrated; the 25 reading categorical bands stay absolute pending a design spike, because what "relative" means for a categorical value is a design question nobody has pretended to have answered yet. One tag, currency, has no rule at all: no grammar signal exists to key on, and it stays absent rather than force-fitted.

08 · Stage 9

The Engine Never Says “Dagger”

Stage 9 is the only stage the player ever reads, and it runs fresh on every inspection because the reader has changed since last time. Everything upstream was about building an honest object; this stage is about presenting it without ever handing over the answer key.

Neutral by construction

Every artefact carries a physicalLabel generated from observable properties alone: "short bronze elongated form with engraved disc-form attachment". The word "dagger" appears nowhere, because "dagger" is an interpretation and interpretive naming is the player's job. The occluded groundTruthTags exist solely so the engine can later judge claims against reality; no agent's interpretive model, player or NPC, ever reads them.

Registers: same facts, different foregrounding

Descriptions are filtered through registers, which shape framing without touching truth. The spec's worked example describes one wear pattern five ways: neutrally, "marks are visible along the edge"; functionally, "repeated use-wear consistent with cutting or scraping"; aesthetically, as a patina of handling; ritually, as possible deliberate decommissioning of the blade; technically, as deformation from contact with something harder than the blade. All five are true. Each forecloses different follow-up questions, which is precisely why acquiring a register matters to the player. MVP ships three registers (observational, interpretive, technical); the five-register acquisition system with per-domain proficiency is designed and explicitly deferred.

One authoring constraint deserves its own line: a relative tag must never be described as an intrinsic property. A template rendering elite as "an object of obvious wealth" misrepresents what the score measured, which was standing against the producing culture's own norms. The constraint is written into the template contract, so the prose layer can't quietly undo page 07's careful semantics.

The lens sits on top

The interpretive lens (the game's core mechanic, specced in its own document) selects which template variants surface and how observations are ordered: high-salience observations up front, the rest behind investigation, suggested tags nudged by the player's published claims. The presentation type keeps the honest raw data one drill-down away at all times, and the lens's hard limits repeat from page 01: reorder, reframe, de-emphasise, nothing else. A player who has published "Culture A was a warrior society" will find blades foregrounded and weaving tools easy to scroll past. The engine isn't lying to them; it's agreeing with them, which is worse.

What exists today

The observational register is real: authored templates per primitive, an expander for #slot# placeholders with article handling, and deliberate drop-on-none semantics (a sentence referencing an absent or none-valued parameter is dropped whole rather than rendered with a hole; where "none" is itself observable, like a sealed vessel's opening, a dedicated variant handles it). The renderer is shared by the CLI samplers and the Explorer's structure viewer, one implementation on both surfaces, so the dev tooling's voice and the eventual description engine's observational voice cannot drift apart. Variant selection currently gates on parameter values only; register filtering, lens alignment and material-aware gating are the full description engine's job, a scheduled roadmap task that supersedes the minimal renderer.

09 · Stages 1–3

The World Is Still a Fixture

The pipeline's first three stages produce the world the other six consume: chronology, cultures, geology and a simulated body of scholarship. They are specified in detail and not yet built. The engine currently runs against four preset cultures and six named fixture worlds, and the seams where the real thing will bolt on are marked in the code.

Chronology without a shared timeline

There is no monolithic world timeline. Each culture has its own periodisation, and interactions are defined by temporal overlap rather than shared phase labels; Culture A's "Expansion" might overlap Culture B's "Settlement" and the player has to work the alignment out from stratigraphy. An artefact's true age is the gap between the world's present year and its production year, and that number is hidden. Relative dating comes free from stratigraphy; approximate frameworks come from the corpus (and may be wrong); commissioning independent radiocarbon or thermoluminescence dating is a career-gated action that takes time, may consume part of the artefact and can overturn the received framework. "The accepted chronology for Site X is wrong" is a publishable, high-scrutiny claim.

Relationships are windows, never verdicts

Culture relationships are sequences of dated phases, each carrying simultaneous trade, conflict, exchange and political dynamics; two cultures can trade in one window and raid in another, or both at once. Material flows ride on those windows, which is what stage 6's trade-only rescue and stage 7's borrowed motifs consume. The design intent is that a foreign material or motif never has a unique explanation, because the relationship data genuinely supports several.

A profession that predates the player

Stage 3 is the strangest and best idea in the world design: before the player exists, the engine simulates decades of scholarship. NPC scholars are generated with specialisations, site preferences and career stages, each carrying an InterpretiveModel, the same agent-generic interface the player uses. They "excavate" sites biased by their interests, publish through the same document structures the player will use and aggregate into a professional corpus: reference works, active debates, bibliographies and conspicuous absences a careful player can notice. Coverage is deliberately unequal (burials before middens, prominent cultures before modest ones) and the gaps are the player's opportunity space.

Calibrated wrongness The corpus targets roughly 70% broadly correct, 30% interestingly wrong: right about common materials and forms for well-studied cultures, wrong through biased site selection ("a warrior society", concluded from only digging fortifications), false absence claims, bad rarity assessments and missed contacts. NPC errors are real claims in real interpretive models diverging from occluded ground truth, never ad-hoc "wrong" flags. The player's own publications are later measured against this baseline, from safe confirmation up to maximum-scrutiny novelty, which is what makes parroting consensus a career plateau by mechanism rather than by authorial punishment.

What stands in meanwhile

Four authored Explorer culture presets (Thalassar is the one with a taste for precious metal) and six named regional fixture worlds that model availability for all sixteen materials. That last detail matters: an earlier mock world modelled only four materials, and everything unmodelled passed an "unmodelled means obtainable" lenience at full weight, which skewed a 1200-artefact calibration sample badly enough that silver ranked as the world's second commonest material. Fixtures are world design too; an unrepresentative fixture calibrates the system to a world that will never exist. MVP scale for the real thing: two cultures with 3–4 phases each, one relationship with two temporal windows, three to four NPC researchers, six to eight simulated campaigns, fifteen to twenty baseline publications.

10 · Working Practices

The Spec Argues Back

The pipeline is one artefact of a working method, and for a developer arriving cold the method may be the most transferable thing in the repository: a spec that accumulates its own corrections, constants that get measured before they're believed, and generation you can watch.

Docs that carry their own errata

The design spec is fourteen numbered documents, and doc 05, the generation architecture, is written in an unusual discipline: when implementation contradicts the spec, the spec keeps its original text and gains a dated implementation note explaining what shipped instead and why. The gilding correction sits inline where the wrong sentence used to be. The decoration depth table stays in the doc with a note proving its middle corners unsatisfiable. You can read the document as an argument the project had with itself, with timestamps. Two companion structures keep it coherent: a propagation register (doc 12) logs every change that ripples across documents until the ripple is applied, and design spikes get standalone write-ups holding the reasoning while the ruling propagates to the reference docs. Every task has a stable id (2GN.84, 3WS.7) that code comments, docs and the roadmap all cite, so provenance survives across all three.

Constants are measured before they're believed

The recurring loop, visible on pages 05 through 07: author a provisional constant, mark it MVP-provisional with the precedent it follows, build the observability to sample real output, measure, then either pin the constant with a calibration test or replace it with a measured value and record the distribution table in the doc. The classification thresholds went through the full loop twice (the second pass caught the fixture skew). The scarcity weights kept their authored values but gained a test that pins the ratios between rungs, which is the honest version of "these numbers are right": nobody claims 0.25 is correct, only that scarce reading meaningfully rarer than available is now load-bearing and protected.

Why this matters more here than in most software A procgen system fails statistically. Every individual artefact can look fine while the population is absurd (nine in ten objects "elite", a metal-free culture leading the world in wirework; both real, both caught by sampling). Unit tests assert properties of instances; this project's calibration suites assert properties of distributions, and that's the difference between testing the generator and testing its outputs one at a time.

The engine boundary

Everything under engine/ is pure TypeScript: no Svelte, no browser, no ambient randomness, PRNG injected. The UI layer is a consumer. This is what makes the same pipeline runnable headless in tests, from CLI samplers and inside the browser workbench with identical output, and it's enforced socially by module JSDoc and structurally by the import graph.

Generation you can watch

Two observability surfaces grow with the pipeline. The Project Explorer (dev builds only) is a nine-panel browser workbench: PRNG output, a live type index with dependency graphs, structure viewer, plausibility panel, material viewer, decoration inspector, tag inspector and rule calibration. The CLI samplers (deno task sample:artefact, :materials, :decoration, :features, :classification) print one pipeline stage each, with per-value provenance in the classifier reading. The roadmap treats observability as a deliverable of every phase rather than tooling debt, and the calibration stories on earlier pages are the payoff: most of the interesting bugs were found by looking at output distributions, and you can only look at what you've made visible.

Reading order, if you go to the source

Start with doc 02 (six design pillars; Simulation Honesty and Error Is the Engine explain most decisions on these pages), then doc 03 (the systems map), then doc 05 with these pages beside it. For code, engine/prng.ts then engine/generation/grammar.ts top to bottom; the module JSDoc blocks are the real documentation, and they're written to be read.
