Those Who Came Before
Engineering Notes · Generation Pipeline

How an Artefact Gets Made

Those Who Came Before is a game about an archaeologist whose mistakes compound into an unreliable narrative. For that to work, the things being misinterpreted have to be real: every artefact is a physical object generated from a seed, with a structure, materials, decoration and a ground truth the player never reads directly. These pages explain how that generator works, in the order the pipeline runs.

Written for developers who build software but haven't built procedural generation. No prior archaeology required; no prior game development either.

Stages 1–9 · Pipeline overview

Nine Stages, Three Cadences

Every artefact the player will ever touch has passed through nine stages, in order, at three cadences: three stages run once per world, five run per artefact and one runs per inspection.

The spine

World Seed
  → Chronology & Culture Generation        (once per game)
    → Initial Corpus Generation             (once per game)
      → Bottom-Up Structural Grammar        (per artefact)
        → Normalisation + Plausibility      (per artefact)
          → Material Assignment             (per artefact)
            → Decorative Grammar            (per artefact)
              → Feature Extraction + Tags   (per artefact)
                → Description Generation    (per inspection)

Stages 1–3 run once, at world creation: they produce the chronology, the cultures, the geology and a simulated century of scholarship for the player to inherit. Stages 4–8 run every time the world needs a new artefact, building a physical object, dressing it and scoring it against the tag vocabulary. Only stage 9 repeats per inspection, because the player's beliefs and available registers shift between viewings; the same object can read differently on Tuesday than it did on Monday.

Structure first, meaning last

The grammar in stage 4 produces geometry with no idea what it's for; classification in stage 8 reads that geometry back and scores it against functional tags; the description in stage 9 hedges even those scores through registers and the player's interpretive lens. Nothing upstream ever branches on "make a sword".

Visibility levels

Every property the pipeline produces sits at one of four visibility levels, and the level is part of the type system's contract.

LevelMeaningExamples
ObservableDirectly perceptible on inspectionComponent structure, decoration layers, material identity
InferableRecoverable by reasoning from observablesMaterial provenance, motif significance
OccludedGround truth the player can only inferChronology, culture profiles, true tag scores
Engine-internalNot a world fact at allThe seed, plausibility checking, corpus simulation

The interpretive lens (the game's core mechanic) operates on observable and inferable properties only. It can reorder, reframe and de-emphasise; it cannot reveal occluded properties and it cannot hide observable ones. Every wrong belief the player forms traces back to their own filtering.

What exists today

The implementation restarted from scratch for launch and is being rebuilt against a 318-task MVP roadmap; 89 tasks were done at the time of writing. Milestone 1 (runtime, the full type system, the seeded PRNG, the developer workbench) is complete. Milestone 2 is the generation pipeline itself, at 49 of 101 tasks.

  • Stages 4–8 are shipped as pure TypeScript engine modules: grammar expansion, normalisation, plausibility, materials, decoration, feature extraction and classification, each with its own test suite.
  • Stage 9 is partial. The observational register's templates and a minimal renderer exist; the full description engine (variant selection, register filtering, lens integration) is a later roadmap task.
  • Stage 1 shipped with Milestone 1: the seed machinery is real, tested and drives everything below; the determinism page covers it.
  • Stages 2–3 are designed but not built. The engine currently runs against mock cultures and six fixture worlds. The world page covers them.

Foundation · Seeding & determinism

Every Draw Is Accounted For

The entire game world unfolds from one seed string. Same seed, same world, same sequence of artefacts, on every machine, forever. That guarantee rests on a module about a hundred lines long and two habits: every generation function takes the PRNG as a parameter, and no function changes how many draws it makes.

The generator

The seed string is hashed by xmur3 into a stream of well-mixed 32-bit integers, which seed the four state words of a xoshiro128** generator. Each call advances the state and returns a float in [0, 1). There's a guard against the all-zero state (xoshiro is degenerate there; xmur3 makes it vanishingly unlikely, but a guard is cheaper than an incident) and that, with weightedSelect below, is the whole module.

Determinism is injected

No engine module ever calls Math.random(). Every generation function takes a prng: () => number parameter, and determinism flows entirely from that injection. The engine modules are pure TypeScript with no framework or browser dependencies; the design docs call this the engine boundary. The same pipeline runs in a test, a CLI sampler or a browser panel with identical output.

Draw ordering is part of the API

How many times a function draws from the PRNG is part of its public contract. selectGrammarOption documents that it consumes exactly one draw per call regardless of how many options it weighs. If a refactor made it draw twice, every seed in existence would produce a different world, and every regression fixture would be lies. Changing the draw count is a breaking change even when the function's return type is untouched.

Draw order is a wire format In seeded procgen the PRNG call sequence is a serialisation format: the seed is the message and the draw order is the schema. A change to either deserves the review a wire-protocol change gets.

Weighted selection

One utility, weightedSelect, does nearly all the choosing in the pipeline. It takes candidates, a PRNG and a weight callback; the callback shape exists because callers weigh differently-shaped things (grammar options by effective weight, materials by a three-factor product). Two edge cases are handled deliberately: a zero-total weight table degrades to a uniform draw rather than crashing or silently picking the first item, and floating-point drift on the final subtraction falls through to the last candidate.

export function weightedSelect<T>(
  items: readonly T[],
  prng: () => number,
  getWeight: (item: T) => number, // callers weigh differently-shaped things
): T

What the seed does and doesn't pin

The guarantee is phrased carefully: same seed means the same sequence of artefacts. Artefact N may depend on artefacts 1 through N−1 (associated finds, site reuse, material precedent), so the seed determines the unfolding, and no artefact is addressable in isolation. If you want artefact 500, you generate the 499 before it.

Stage 4 · Structural grammar

The Grammar Doesn’t Know What a Sword Is

Stage 4 builds the physical object. It works bottom-up from geometric primitives, and it is forbidden, as a matter of design law, from ever branching by intent. The spec marks exactly one principle non-negotiable, and it's this one.

Why bottom-up

The obvious way to generate game items is top-down: pick "sword" from a table, then fill in sword-shaped details. The whole game premise dies if you do that. If the generator knows it made a sword, the classification is trivially recoverable and interpretation has nothing to do; the player's job of working out what a thing was only exists if the engine itself never decided. So the grammar produces structures (an elongated form with an edge, socketed to a cylindrical form) and classification happens downstream, by reading the geometry back like an archaeologist would. The ambiguity is native: a long edged thing genuinely might be a weapon, a tool or a ritual object.

The vocabulary

Eight geometric primitives, each with its own parameter set: elongated, cylindrical, flat-broad, hollow-enclosed, ring-form, disc-form, bar-form, sheet-form. Two examples of the parameter space:

  • An elongated form has a length band, a cross-section, a taper, an edge count and a point: enough to be a pin, a blade or a shaft, without ever saying which.
  • A hollow-enclosed form has a shape, wall thickness, an opening and a base: enough to be a jar, a box or an urn, same rule.

Components join through nine attachment types (inline, perpendicular, socketed, riveted, wrapped, lashed, hinged, threaded, friction-fit), and the attachments matter later: a hinged join is evidence of fine metalwork, and classification will read brooch anatomy off a pin bearing on a hoop.

<object>            ::= <component-group>+
<component-group>   ::= <primary-component> [<attachment> <component-group>]*
<primary-component> ::= <elongated> | <cylindrical> | <flat-broad>
                      | <hollow-enclosed> | <ring-form> | <disc-form>
                      | <bar-form> | <sheet-form>

The BNF's repetition operators are engine-owned: the data module supplies alternatives and weights only, and expandGrammar decides how many groups and how long the attachment chains run, bounded by the complexity budget below.

Grammar rules live in a data file as plain objects; the engine looks them up by symbol. Four production rules cover the MVP.

Culture is a weight modifier

Cultures don't have allowed artefact types. They have tendencies, expressed as weight modifiers over grammar options. Selection works like this: start from the option's authored base weight, add each cultural modifier scaled by the culture's affinity for that material tag, multiply by phase influence, floor at 0.01.

weight = max(0.01,
  (baseWeight + Σ affinity(tag) × modifier)
  × Π (1 + (multiplier − 1) × phaseAttribute))

The 0.01 floor means nothing is ever impossible: a deeply pacifist culture occasionally produces a blade. The source comment reads, in full, "Because archaeology." Phase influence is calibrated so a high attribute amplifies while a low one merely fails to amplify; "low metallurgy" never drags an option below its base weight.

A phase is a multi-attribute profile, one per culture per period: eight technology axes (metallurgy, ceramics, textiles, leather-working, stone, glass, wood, bone), plus economy, society and aesthetics blocks. A culture can be exceptional metalworkers with crude ceramics, and its artefacts will say so.

Complexity budgets and arrangement patterns

Uncontrolled repetition produces nonsense, so repetition is patterned, and the constraint system encodes two claims about the world rather than two knobs on a generator.

The budget is a claim about people

Object complexity tracks who a culture can afford to specialise: a part-time potter makes simple forms, a workshop tradition supports composite objects with several distinct assemblies. So the budget hangs off society.craftSpecialisation, one number per culture-phase, resolved into a tier that every object draws against:

  • Simple (0–0.3): 1–2 component groups, basic patterns only (symmetric, linear).
  • Moderate (0.3–0.6): 2–3 groups, most patterns available.
  • Sophisticated (0.6–1.0): 3–4 groups, all six patterns, including nesting and branching.

Complexity is a property of the society before it's a property of any object, which is why the budget binds at the culture level and not per artefact.

The patterns are a claim about objects

Real artefacts repeat components deliberately: rivets march in rows, beads circle a rim, sockets stack. Six arrangement patterns cover the MVP (symmetric pairs, radial spreads of 3–12, linear arrays, stacks, nests, branches), and a repeated component must belong to one of them; the accumulation checker rejects an expansion whose repetition fits no pattern, because unpatterned repetition reads as noise where patterned repetition reads as intent. The arrangement group survives normalisation, so downstream feature extraction can tell a radial spread of studs from one stud, and the player can too.

Portability, derived

Generated objects carry a portability band, from pocketable through team-lift to major-effort, and an inspection depth derived from physical dimensions: anything up to 30cm can be held and fully examined, up to 150cm examined in detail, beyond that observed in situ. These are mechanical facts about player handling, and classification rules are banned from reading them; the classification page has the boundary and the test that guards it.

Stage 5 · Normalisation & plausibility

Exhaustion Throws

The grammar is honest about geometry and ignorant of physics. Stage 5 flattens its tree into a normalised structure, then checks the result against physical plausibility rules. On failure it re-rolls; on exhaustion it refuses to emit anything at all.

Normalisation

Grammar expansion yields a tree; downstream stages want a flat, standardised shape. NormalisedArtefact carries the component list (each with its primitive type, parameters, position along the primary axis and arrangement-group membership), the attachment list, derived dimensions, portability and inspection depth. The spec also makes normalisation the owner of allowedMaterialTags per component, derived from a physical compatibility table: an edged elongated form admits metal and stone; a hollow-enclosed form admits clay, metal, wood and stone. Physics supplies these constraints; the grammar never did. In the shipped code the field is stubbed empty (its compatibility table is a scheduled task, 2GN.10, and the stub is labelled as such at the assignment site), and the convention downstream is that an empty list means "no constraint recorded yet" rather than "nothing fits".

The rule set

type PlausibilityRule =
  | { type: 'requires';  component: string; dependsOn: string }
  | { type: 'excludes';  component: string; excludes: string }
  | { type: 'ordering';  component: string; before?: string; after?: string }
  | { type: 'material-physics'; predicate: (a) => boolean; reason: string }
  | { type: 'ergonomic';        predicate: (a) => boolean; reason: string }

The rules encode things a craftsperson would never build: an edged form with nothing grippable attached, a long blade on a stubby grip, a heavy head lashed to a cord, a heavy component perched on a thin-walled vessel. Each predicate rule carries a human-readable reason; a failed check is a diagnostic. The five shapes are five kinds of impossibility:

  • requires / excludes carry affordance logic: an edged form demands something grippable, because a blade nobody could hold is a blade nobody would have made.
  • ordering carries assembly logic, constraining which components can precede which along the primary axis.
  • material-physics rejects configurations that fail statics: the heavy head on the thin-walled vessel.
  • ergonomic encodes the one constant every culture in every generated world shares, the human body. A long blade demands at least a medium grip because wrists are wrists everywhere; this is the only rule family that holds across all possible cultures by construction.

The set is written negatively, and the direction is a design decision. Enumerating everything a craftsperson might build is open-ended; enumerating what nobody would build is tractable. The rules stay as ignorant of function as the grammar: they know certain geometry could never be used by human hands, whoever made it and whatever it was for.

The exhaustion contract

When plausibility fails, the pipeline re-expands from stage 4 and tries again, up to N attempts. Grammar expansion is cheap; re-rolling is the intended control flow. If all N attempts fail, the contract (assigned to a scheduled roadmap task; checkPlausibility is shipped, the retry orchestration around it comes with the pipeline assembler) is to throw a typed PlausibilityExhaustedError carrying the seed, the attempt count and the last failing rule set.

Why throwing is correct here Exhaustion means the grammar and the rule set disagree: a generator defect to surface during development. A relaxed rule set would break the pipeline guarantee that every artefact reaching the player passes every plausibility rule. A fallback artefact not derived from the grammar would break Simulation Honesty, the design pillar that says all player-facing content derives from the same underlying data. The strongest case for a fallback is availability (a live game that throws is worse for the player than one that shows a slightly wrong pot); the project's answer is that the error is a development-time signal by construction, because determinism means any exhausting seed can be reproduced and fixed before release.

The guarantee

The pipeline promises structural coherence unconditionally: no artefact that fails a plausibility rule ever reaches the player, and the promise holds vacuously through exhaustion because in that case nothing reaches the player.

Stage 6 · Material assignment

Fake Relics Obey Real Geology

Materials are assigned per component, and assignment is the first stage that consults the world beyond the object: what the region's geology offers, what the culture prefers, what its technology can work at this point in its history.

The catalogue

Sixteen materials, each a definition with tags, availability data and physical properties: bronze, iron, gold, silver, obsidian, flint, granite, jade, oak, ash, bone, antler, fired clay, glass, linen, leather. Tags group them (metal, stone, wood and so on) so that component compatibility can be expressed against kinds while selection lands on specifics.

Selection: two filters, a ladder, one product

  1. Compatibility filter. Keep materials whose tags intersect the component's allowedMaterialTags; an empty constraint list admits everything.
  2. Availability filter. Keep materials obtainable in this geology, locally or via a trade flow.
  3. Fallback ladder. If availability empties the pool, fall back to the compatible set; if that's empty, the full catalogue. The function never hands weightedSelect an empty list, so it never throws on a populated catalogue.
  4. Weighted draw. Survivors are weighted by the product culturalAffinity × phaseTechnology × scarcity.

Availability is a five-rung ladder per material per region: abundant, available, scarce, trade-only, absent. A trade-only material is rescued by a matching MaterialFlow in an active relationship window; an absent one is excluded outright. Scarcity then weights the survivors: 1.0, 0.6, 0.25, 0.15 down the rungs. A scarce material still appears, just rarely, and a trade material arrives at the doc's "present but uncommon" level.

// materials.ts: pinned by the calibration suite as ratios, not absolutes
const SCARCITY_WEIGHT: Record<string, number> = {
  'abundant':   1.0,
  'available':  0.6,
  'scarce':     0.25,
  'trade-only': 0.15,  // "present but uncommon" (doc 05 §7)
  'absent':     0,     // never reached: isAvailable excludes it first
};
// per surviving material:
// weight = culturalAffinity × phaseTechnology × SCARCITY_WEIGHT[level]
Weights are ratios, and the tests know it No document anywhere specifies "12% bronze". The spec states priorities directionally and explicitly disclaims quota readings; the numbers above are authored, marked MVP-provisional. What stops a typo silently reshaping the world is a calibration test suite that pins the distribution: per-region tag shares, splits within a tag (how metal divides into bronze, iron, gold, silver) and a provenance mix sensitive specifically to the trade-only rung. Before that suite existed, the distribution tests were bare directional inequalities that would pass for any descending set of four numbers; nothing could tell a deliberate recalibration from a slip. That gap, and the fix, are recorded in the doc itself.

Provenance: the engine remembers, the player infers

Provenance answers a different question from findspot. Where an artefact was dug up belongs to stage 2 (the site, the layer, the deposition); where its raw material came from is decided here, at assignment time, because the answer depends on world state no later stage can reconstruct.

Trade windows close; a query run centuries later, against the world as it ended up, would get a different answer from the one that was true when the object was made. So the engine records the answer at the moment it's determined:

  • Source: local, regional, trade or unknown. A mechanism, never an intent.
  • Likely origin region: where the raw material plausibly came out of the ground.
  • Trade-path reference: which relationship window carried it, when trade did.

All of it is hidden, and the hiding is the game design. A traded ingot, a looted trophy and a diplomatic gift can leave identical material signatures, so the player who sees a copper object from a culture with no copper deposits has to construct the explanation themselves; trade, migration, conquest, a stolen trophy and a misattributed culture are all live hypotheses, and the relationship data upstream genuinely supports several of them.

The engine's record exists so that a player's provenance claim can eventually be marked right or wrong against something.

Physical properties feed the next stage

Each material definition carries seven authored physical axes plus a keyed reactivity object, and each axis earns its slot by splitting a pair of materials that some downstream check must treat differently. An earlier model with a vague workable axis was retired for conflating brittleness, pliability and grain coarseness; these are the axes that replaced it, with the catalogue's own values.

AxisWhat it measuresThe values that justify it
hardnessScratch and dent resistance, on the real Mohs scaleFlint 7, granite 6, bronze 4, gold 3, leather 1. The real scale keeps authored data auditable: granite below gold would be catchable with a geology book.
fragilityHow it fails: shatter against deformGlass 7 (the value the axis was introduced to capture), obsidian 6, jade 2, gold 1. Jade is harder than obsidian and far tougher; hardness can't predict shattering, so it can't stand in for this.
rigidityHolds its shape under forceGranite and fired clay 7, oak 5, leather 2, linen 1. Gilding gates here: leaf needs a surface that stays put.
grainFinenessThe precision cap on worked detailGold 7 (why chasing reaches such fine detail), obsidian 7 (a true glass), granite 3: coarse visible crystals cap fineness however carefully the mason works. The granite case is the one that motivated the axis.
porosityAbsorbencyFired clay 6, the physical reason glazing exists as a technique; oak 4 takes stain and paint readily; vitrified glass 1.
combustibilityIgnition behaviourLinen 7 (ignites near 210 °C), oak 5 (around 300 °C), fired clay 1: already fired, inert in this range.
formabilityWhether it can be given a raised form, read at the working stateFired clay 6 (read wet, a true plastic state), the metals 5 (cast or forged), granite 4 (pecked in controlled increments), leather 3 (wet-moulded or tooled), obsidian and flint 1: knapping is controlled fracture, unsteerable into relief. Splitting granite from obsidian is the job the axis exists to do.
reactivityChemistry, one value per key; oxidisation so farIron 7 (rust), bronze 6 (verdigris), silver 3 (tarnish), gold 0, stone and glass −1. Gold's 0 is deliberate against the minerals' −1: gold has oxidation chemistry and famously resists it; a mineral has none to speak of.

One real entry, so the shape is concrete:

// data/materials.ts (comments abridged)
{
  id: 'obsidian', tags: ['stone'], craftDomain: 'stoneWorking',
  physicalProperties: {
    hardness: 5,      // Mohs 5–5.5: genuinely softer than flint, despite feeling sharper
    fragility: 6,     // textbook conchoidal fracture; flakes under a mis-strike
    rigidity: 7,
    grainFineness: 7, // a true volcanic glass: knapped edges sharper than steel
    porosity: 1,
    combustibility: 1,
    formability: 1,   // removal can't be steered into a raised form
  },
  reactivity: { oxidisation: -1 },
  decorability: { engravable: true, paintable: false, glazeable: false },
}

Obsidian's row is the axes doing their job in one material: its edge comes from fracture behaviour and grain, its hardness is unremarkable, and no single "workable" number could carry those three facts at once. Formability is the one axis read at the working state where the other six describe the finished object; fired clay is modelled wet there (6) and shatter-prone everywhere else (fragility 6), and the docs record that single-state inconsistency with the task id that owns resolving it.

Scaffolding, labelled

Milestone 2 runs this stage against mock world fixtures, and the module JSDoc records the consequences: there's no culture-to-region mapping yet, so availability answers "obtainable anywhere in this geology" rather than gating on the artefact's eventual findspot region, and the trade-path id is a synthesised string because relationships don't carry stable ids yet. Each shortcut names the roadmap task that retires it.

Stage 7 · Decorative grammar

Every Layer Is an Act of Craft

After structure and materials, a second grammar runs over the artefact, treating each component as a potential canvas. Decorative features feed the same unified classification as structural ones: an object can read as ritual because of its shape, because of its decoration or because of both.

Sixteen techniques, three families

The decorative BNF has three categories: surface treatments (polish, patina, roughening, scoring, engraving, relief, painting, glaze), applied elements (inlay, overlay, studs, wire-wrapping, gilding) and textile elements (wrapping, tassels, beading).

<decoration>        ::= <surface-treatment>* <applied-element>* <textile-element>*

<surface-treatment> ::= polish | patina | roughening | scoring
                      | engraving(<motif>)            [requires: holds an incised line]
                      | relief(<motif>)               [requires: formability ≥ 3]
                      | painting(<motif>, <pigment>)  [requires: solid surface]
                      | glaze(<colour>)               [requires: ceramic]

<applied-element>   ::= inlay(<material>, <motif>)      [requires: engravable surface]
                      | overlay(<material>, <coverage>) [requires: rigid surface]
                      | studs(<material>, <pattern>)
                      | wire-wrapping(<material>, <pattern>)
                      | gilding(<precious-metal>)

<textile-element>   ::= wrapping(<material>, <pattern>) | tassels | beading(<material>)

The families are three different relationships between decoration and object:

  • Surface treatments rework material already present: engraving, scoring and polish remove or rearrange, and their evidence is toolmarks in the substrate itself.
  • Applied elements bind a second material onto a surface, so each one is also a supply decision.
  • Textile elements attach flexible material at anchor points, and they answer to a different technology axis (spinning and weaving) than the metalwork most applied elements lean on.

The <material> arguments in the BNF are doing real work: seven of the sixteen techniques bring a material of their own, on top of whatever the component is made of.

  • The introduced material is a genuine assignment: constrained by per-technique tag sets (wire-wrapping introduces metal; wrapping, fibre or leather) and weighted by the same affinity × technology × scarcity product stage 6 used, gated on the culture actually being able to obtain it.
  • An inlaid panel is two supply chains in one object, each able to carry its own trade story; the wire-wrapping defect below sits exactly on this seam.
  • The extra cost is why appliedElementCount is one of classification's discriminating signals: adding material is dearer than reworking what's there.

Each technique also declares a substrate prerequisite, resolved against the material property axes from stage 6:

  • Engraving requires a material that can hold an incised line; soft precious metals qualify via chasing and repoussé despite not being structurally hard. The gate is workability.
  • Relief requires formability ≥ 3: the material must take a raised form at all. The earlier rigidity proxy wrongly admitted obsidian and flint (worked only by conchoidal fracture) and wrongly excluded leather (tooled or wet-moulded into relief for millennia).
  • Gilding gates on rigidity. The spec once said "you don't gild wood", and that sentence has been removed as factually wrong: gilded wood over gesso is the commonest gilding in the historical record. The doc keeps the correction inline, dated, with the reasoning.

Technique choice and imagery are independent signals

A culture's preference for techniques (techniqueAffinities) is deliberately separate from its motif vocabulary and from its material affinities. A culture can engrave beasts, engrave without beasts, depict beasts without engraving or do neither; those four combinations only exist if the two signals vary independently, so the type system keeps them apart. On top of affinity sits a one-directional material-access gate: a culture with no suitable material in plentiful, favoured supply has the technique suppressed however much it "likes" it, but favouring a suitable material never forces the technique.

The wire-wrapping defect The gate originally checked only a technique's substrate. Wire-wrapping's substrate is the grippable form it wraps, which is fine; the metal wire is a material the technique introduces, and that side went unchecked. A sampling pass found the result: metal-free cultures produced more metal wirework than anywhere else in the world. The gate now checks both what a technique sits on and what it brings with it. Semantic bugs like this pass every type check and every unit test written from the same mental model; the Explorer page covers the harness that caught it.

How much, versus how well

The spec described a 2×2 of craft skill against decorative emphasis, controlling recursion depth. Measured against the real pipeline, its two middle corners ("technically refined but sparse", "abundant but simple") proved unsatisfiable by any single volume scalar, because they differ in kind rather than magnitude. The shipped design splits the axes into two mechanisms:

  • Volume (layers per component) reads the culture's decorative emphasis alone: how much decoration a culture puts on things.
  • Grade (a 0–1 execution quality per layer) reads craft specialisation scaled by the technique's own difficulty: polish and scoring sit at the easy end, inlay and gilding at the hard end.

Craft keeps one legitimate indirect effect on volume: high-craft cultures build more complex objects, and more parts means more canvases.

Grades get a second pass once materials are known, because execution difficulty is material-sensitive: engraving iron and engraving gold no longer score identically. Classification later reads mean decorative grade as a quality signal independent of quantity, so a sparse, superb object can outrank a busy, clumsy one.

Motifs, borrowed and otherwise

Motif-carrying layers draw from the producing culture's motif vocabulary, weighted 1, plus motifs borrowed through any cultural-exchange relationship active in the production year, weighted by that window's exchange intensity. Introduced materials for techniques like inlay are constrained to per-technique tag sets and weighted by the same affinity × technology × scarcity product as structural assignment. An artefact bearing Culture B's motifs might be B's work, or A's work under heavy exchange, and the sequence of layers (base engraving in one vocabulary, later inlay in another) hints at reworking without any flag saying so.

Deliberate gaps

Layers currently ship flat: sublayers is always empty, and decoration-on-decoration is a scheduled task rather than an accident. Substrate enforcement strips candidate layers whose component's actual material fails the prerequisite, except for the three form-substrate techniques (wire-wrapping, wrapping, beading), which pass through unstripped because nothing in the pipeline can yet answer a geometry question about a component; stripping on a check that cannot run would delete three techniques from every artefact on no evidence. The module JSDoc lists each gap, its owner and its reasoning.

Stage 8 · Features & classification

Tags Are Evidence Tallies

Stage 8 is where the pipeline reads its own output back. A single extraction pass turns the finished object into a feature set; 43 scoring rules turn features into tag scores. The scores are the game's occluded ground truth: the player's claims are eventually judged against them, and the player never sees them.

Extraction: one pass, one value per question

extractFeatures runs once across components, attachments and decorative layers together, and it's pure and PRNG-free: same artefact in, same features out. An artefact can have three edged components. Which one is "the blade"? Every multi-component collision resolves to one value through a documented collapse policy:

  • Blade fields read from the dominant edged component (longest, earliest position on ties), so length band and profile never describe different blades.
  • Container fields read from the dominant container (largest hollow-enclosed, falling back to longest cylindrical), so a bowl with a socketed ferrule reads the bowl's opening and base, never a mix.
  • Categorical fields like perforation collapse to the most classificatorily loaded value present, with the priority order pinned in comments.

Some features have no single grammar signal and are derived from interviewed anatomy rules instead:

  • Impact surface: an untapered bar end or a thick disc. A plain bar end is a striking face; think hammer, pestle, mace head.
  • Fastening mechanism: brooch anatomy (a sharp, edgeless pin bearing on a hoop) or any hinged join, gated to body scale.
  • Wearable: a ring form or a suspension perforation, gated the same way, because a hinged chest lid is not a dress fastener and nobody wears a perforated slab.

The presence flags deliberately refuse the module's own graceful-degradation contract: unrecognised signals leave them false, so degradation can never fabricate a pin.

A boundary with a test on it No classification rule may read portability or inspectionDepth. Both derive from the same dimensions as the physical massBand and sizeBand, but they are mechanical facts about player handling, and letting classification consume them would smuggle game mechanics into world semantics. Rules read the physical bands instead, and a boundary guard test fails the suite if any rule ever touches the mechanical pair.

Scoring: a plain sum, on purpose

classifyArtefact runs all 43 rules and folds every matching rule's tag weights into one map by plain unbounded sum, iterated in canonical vocabulary order. No normalisation, no softmax, no cap. The JSDoc pins what the numbers mean: "evidence tallies, not confidences". Consumers compare by rank and margin and read absent tags as zero. An engraved bronze blade scores on weapon, ritual, ceremonial and elite simultaneously, and the system leaves the tension unresolved because resolving it is the player's entire job.

// the rule shape (shipped rules live in data/classification.ts; weights here illustrative)

  condition: (features: ExtractedFeatures, context: ClassificationContext) => boolean;
  tags: Map<ArtefactTag, number>;
}

Absolute tags, relative tags

The vocabulary splits by scoring basis, and the two halves make two different kinds of claim.

BasisThe claimTagsThreshold
AbsoluteAbout the object: affordances a lone examiner could verify with the thing in handweapon, tool, container, fastener, ornament, domestic, agricultural, maritime, trade-good, currencyFixed
RelativeAbout a population: this object sits in the upper tail of its own culture's outputpersonal, communal, elite, utilitarian, ceremonial, everyday, military, artisanal, ritual, votive, funerarySampled per culture-phase

The failure that forced the split

Under absolute thresholds, the applied-element rule fired on 4.3% of artefacts from an austere culture and 48.1% from a decorative one, an order of magnitude of phase sensitivity; "elite" had quietly come to mean "unusually decorated in absolute terms", so a decorative culture read as composed almost entirely of elites. That breaks Simulation Honesty directly, and the fix follows the tag's semantics: elite means unusually rich for this culture, so the threshold has to come from this culture's own distribution.

Whose distribution?

A population claim means nothing until you say whose. Four populations could anchor it:

  • Every artefact in the world: reproduces the measured failure; decorative cultures become aristocracies wholesale.
  • The profession's published corpus: ground truth would depend on what happens to have been excavated, and the pipeline guarantees ground truth is lens-independent.
  • The player's personal finds: the same problem, with a smaller and stranger sample.
  • The producing culture-phase's own output: the anchoring that matches what the word means. Unusually rich for the people who made it.

Archaeologists reason the same way when they read a grave as rich against the local burial record rather than against Tutankhamun.

The baseline is sampled, never authored

The engine generates 400 artefacts through stages 4–7 for the culture-phase, builds percentile ladders over nine sampled features and scores the real artefact against those. There's no bootstrap circularity, because nothing upstream of classification reads a tag. Sampling also keeps the baseline honest across change: a culture's norm is whatever its own generator actually produces, so retuning any upstream weight moves every relative threshold with it at the next sampling, where an authored baseline would silently drift the first time the grammar changed.

Thresholds come from samples

Measured, then pinned

The spec's illustrative thresholds (decorativeComplexity > 2 and friends) were authored before any decoration pipeline existed. Once one did, sampling 1200 real artefacts showed those thresholds firing on 87–99% of output; under a plain-sum fold, a rule that fires on nearly everything adds a constant to every score and discriminates nothing. The shipped thresholds are pinned to measured percentiles instead, and the doc carries the distribution table:

The sample itself was wrong once

A later re-measurement found the original 1200-artefact sample skewed: the mock geology modelled only 4 of 16 materials, so the other twelve passed an "unmodelled means obtainable" lenience at full weight, and silver came out the world's second commonest material. Re-sampling 7200 artefacts across six fully modelled fixture worlds corrected the material mix and, usefully, proved the elite inflation (steady at ~90% presence in every world) had never been material-driven in the first place.

Ties inflate fire rates

Sampled features are coarse integers with heavy tie-mass, and the comparison is ≥, so a p75 threshold landing on a tie point admits the whole tie and fires at nearly double the implied rate. Each migrated rule records the realised fire rate it was checked against rather than trusting the rung's name.

Where the migration stands

  • 34 of the 43 rules award relative tags, per the split pinned in the test suite.
  • Nine of those had numeric conditions a percentile could replace, and all nine are migrated.
  • The other 25 read categorical bands (wall thickness, base type, mass band and kin) and stay absolute pending a design spike; what "relative" means for a categorical value is still undecided, and the code declines to guess.
  • One tag, currency, has no rule at all: no grammar signal exists to key on, and it stays absent rather than force-fitted.

Stage 9 · Description generation

The Engine Never Says “Dagger”

Stage 9 is the only stage the player ever reads, and it runs fresh on every inspection because the reader has changed since last time. Upstream stages build an honest object; this one presents it without handing over the answer key.

Neutral by construction

Every artefact carries a physicalLabel generated from observable properties alone: "short bronze elongated form with engraved disc-form attachment". The word "dagger" appears nowhere, because "dagger" is an interpretation and interpretive naming is the player's job. The occluded groundTruthTags exist solely so the engine can later judge claims against reality; no agent's interpretive model, player or NPC, ever reads them.

Registers: same facts, different foregrounding

Descriptions are filtered through registers, which shape framing without touching truth. The spec's worked example runs one wear pattern through all five:

  • Neutral: "marks are visible along the edge".
  • Functional: "repeated use-wear consistent with cutting or scraping".
  • Aesthetic: a patina of handling that complements the surface finish.
  • Ritual: marks possibly indicating deliberate decommissioning of the blade.
  • Technical: deformation from contact with material harder than the blade.

They differ in the follow-up questions they invite. MVP ships three registers (observational, interpretive, technical); the five-register acquisition system with per-domain proficiency is designed and explicitly deferred.

The modelling claim behind registers: expertise changes what a description affords rather than what is there. The functional reading points at use, the technical reading at manufacture, the ritual reading at intention, and each one licenses a different next action, which is the currency the game actually trades in.

Registers also explain how the lens stays legal. The pipeline guarantees forbid touching facts, so the only lever a belief system can pull is which true framing arrives first; registers are that lever, typed.

Registers run in both directions

When the player publishes, they choose a register too, and the choice trades credibility against reach:

  • Academic: formal and evidenced; weight with peers, few readers.
  • Curatorial: descriptive and contextualised; moderate on both counts.
  • Popular: reaches everyone, and can spawn simplified versions of the claim that circulate on their own.
  • Field-notes: raw and provisional; minimal credibility, but establishes priority.

The same mechanism that frames what the player reads frames what the profession hears from them.

One authoring constraint: a relative tag must never be described as an intrinsic property. A template rendering elite as "an object of obvious wealth" misrepresents what the score measured, which was standing against the producing culture's own norms. The constraint is written into the template contract, so the prose layer can't quietly undo the relative-tag semantics the classification page set out.

The lens sits on top

The interpretive lens (the game's core mechanic, specced in its own document) selects which template variants surface and how observations are ordered: high-salience observations up front, the rest behind investigation, suggested tags nudged by the player's published claims. The presentation type keeps the honest raw data one drill-down away at all times, and the lens's hard limits repeat from the overview: reorder, reframe, de-emphasise, nothing else. A player who has published "Culture A was a warrior society" will find blades foregrounded and weaving tools easy to scroll past. The engine isn't lying to them; it's agreeing with them, which is worse.

What exists today

The observational register is real, in four pieces:

  • Authored templates per primitive, in data/descriptions/observational/, one file per geometric form.
  • A slot expander for #slot# placeholders, with article handling (#point.a# renders "a sharp point" or "an oval cross-section" correctly).
  • Drop-on-none semantics: a sentence referencing an absent or none-valued parameter is dropped whole rather than rendered with a hole; where "none" is itself observable, like a sealed vessel's opening, a dedicated slot-free variant handles it.
  • One renderer on both surfaces: the CLI samplers and the Explorer's structure viewer share it, so the dev tooling's voice and the eventual description engine's observational voice cannot drift apart.

Variant selection currently gates on parameter values only; register filtering, lens alignment and material-aware gating are the full description engine's job, a scheduled roadmap task that supersedes the minimal renderer.

Stages 2–3 · World generation

The World Is Still a Fixture

The pipeline's second and third stages produce the world everything downstream consumes: chronology, cultures, geology and a simulated body of scholarship. Both are specified in detail and not yet built (stage 1's seed machinery shipped long ago; the determinism page covers it). The engine currently runs against four preset cultures and six named fixture worlds, and the seams where the real thing will bolt on are marked in the code.

Chronology without a shared timeline

There is no monolithic world timeline. Each culture has its own periodisation, and interactions are defined by temporal overlap rather than shared phase labels; Culture A's "Expansion" might overlap Culture B's "Settlement" and the player has to work the alignment out from stratigraphy.

The design mirrors how the discipline works. Archaeologists build local sequences first (this pottery style precedes that one, at this site) and argue about cross-dating second; whole regional chronologies have floated by centuries until an anchor turned up. The engine reproduces that epistemic situation: every culture gets its own phase sequence with its own labels, overlap is a fact about years, and years are hidden. Synchronising two cultures' sequences is publishable work because the world never states the alignment anywhere the player can read.

An artefact's true age is the gap between the world's present year and its production year, and that number is hidden too. Dating arrives on three rungs of increasing cost:

  • Relative dating comes free from stratigraphy: this layer sits below that one, so it's older, and finds in one layer are roughly contemporaneous.
  • Approximate frameworks come from the corpus's received chronologies, presented as established fact, and possibly wrong: the original dating may have been flawed, or extrapolated past its evidence.
  • Independent dating (radiocarbon, thermoluminescence) is career-gated, takes time, may consume part of the artefact and can overturn the received framework. "The accepted chronology for Site X is wrong" is a publishable, high-scrutiny claim.

Relationships are dated windows

Culture relationships are sequences of dated phases, and inside one window the four dynamics run simultaneously: the same pair of cultures can be trading bronze, raiding each other's borders, swapping motifs and sitting in a tributary arrangement in the same decade. Material flows ride on those windows, which is what stage 6's trade-only rescue and stage 7's borrowed motifs consume.

interface RelationshipDynamics {
  trade:            { volume: number; materialFlow: MaterialFlow[]; /* … */ };
  conflict:         { intensity: number; type: 'raiding' | 'territorial' | 'conquest' | 'none' };
  culturalExchange: { intensity: number; domains: ('motifs'|'techniques'|'materials'|'forms')[] };
  political:        { type: 'independent'|'tributary'|'alliance'|'vassal'|'colonial' };
}

Several of those mechanisms move the same evidence: a Culture B ingot in a Culture A hoard is consistent with commerce, tribute, plunder and gift, and the window data can support all four at once. The underdetermination is manufactured deliberately, window by window; a world where every foreign object had one explanation would make the player's judgement decorative.

A profession that predates the player

Before the player exists, the engine simulates decades of scholarship. NPC scholars are generated with specialisations, site preferences and career stages, each carrying an InterpretiveModel, the same agent-generic interface the player uses. They "excavate" sites biased by their interests, publish through the same document structures the player will use and aggregate into a professional corpus. The player meets that corpus as:

  • Reference works summarising what "everyone knows", presented as established fact.
  • Active debates where NPCs disagree and the player can eventually weigh in.
  • Bibliographies attached to claims, so how well-supported a claim is can be assessed.
  • Conspicuous absences a careful player notices: nobody has published on Culture B's burials, or every paper on a region comes from one institution.

The simulation exists because the game's subject is being wrong in company. A lone player against raw ground truth would have nothing to inherit, nothing to cite and nobody to argue with. The agent-generic principle carries the load: because NPC scholars run the same InterpretiveModel as the player, their errors are beliefs held for reasons, reachable by the same evidence the player uses, and overturning one is an argument with a position. Coverage is deliberately unequal in archaeologically authentic ways (monumental cultures over modest ones, burials before rubbish heaps), and the resulting corpus is confidently thorough in some places and silent in others without ever saying which is which.

Calibrated wrongness The corpus targets roughly 70% broadly correct, 30% interestingly wrong: right about common materials and forms for well-studied cultures, wrong through biased site selection ("a warrior society", concluded from only digging fortifications), false absence claims, bad rarity assessments and missed contacts. NPC errors are real claims in real interpretive models diverging from occluded ground truth, never ad-hoc "wrong" flags. The player's own publications are later measured against this baseline, from safe confirmation up to maximum-scrutiny novelty; a player who parrots consensus publishes confirmations and plateaus, by mechanism.

What stands in meanwhile

Four authored Explorer culture presets (Thalassar is the one with a taste for precious metal) and six named regional fixture worlds that model availability for all sixteen materials. A fixture is a small authored world, and every measurement run against it inherits its assumptions. The earlier mock world modelled only four materials; everything unmodelled passed an "unmodelled means obtainable" lenience at full weight, so the other twelve were free everywhere, and a 1200-artefact calibration sample duly ranked silver the world's second commonest material. Nothing in that sample was computed wrongly. The world it measured was wrong, and no assertion inside the run could have noticed. Fixtures are world design too.

The seams for the real stages are typed and waiting:

  • The baseline sampler takes a structural parameter bag rather than a concrete CulturePhase, so real culture generation slots in without changing it.
  • The material module documents which of its answers are region-agnostic pending real geology, each with the task id that retires the shortcut.
  • MVP scale for the real thing: two cultures with 3–4 phases each, one relationship with two temporal windows, three to four NPC researchers, six to eight simulated campaigns, fifteen to twenty baseline publications.

Practice · Measurement culture

Every Constant Is on Probation

Numbers in this codebase have a lifecycle: authored as provisional, exposed to observation, measured against samples, then pinned or replaced. This page covers the lifecycle and the boundary that makes it possible; the Explorer page covers the tooling, and the document-suite page covers the paper trail.

Constants are measured before they're believed

The recurring loop, visible on the materials, decoration and classification pages: author a provisional constant, mark it MVP-provisional with the precedent it follows, build the observability to sample real output, measure, then either pin the constant with a calibration test or replace it with a measured value and record the distribution table in the doc. The classification thresholds went through the full loop twice (the second pass caught the fixture skew). The scarcity weights kept their authored values but gained a test that pins the ratios between rungs, which is the honest version of "these numbers are right": nobody claims 0.25 is correct, only that scarce reading meaningfully rarer than available is now load-bearing and protected.

Procgen fails statistically Every individual artefact can look fine while the population is absurd: nine in ten objects "elite", a metal-free culture leading the world in wirework. Both happened. Unit tests assert properties of instances; the calibration suites here assert properties of distributions.

The engine boundary

Everything under engine/ is pure TypeScript: no Svelte, no browser, no ambient randomness, PRNG injected. The UI layer is a consumer. The same pipeline runs headless in tests, from CLI samplers and inside the browser workbench, with identical output; the boundary is enforced socially by module JSDoc and structurally by the import graph. The measurement culture depends on this: sampling 7200 artefacts is only cheap because the pipeline runs anywhere, and a sample is only meaningful because determinism makes it reproducible.

Practice · The Project Explorer

Generation You Can Watch

Two observability surfaces grow with the pipeline: a nine-panel browser workbench compiled into dev builds at /dev/explorer, and a CLI sampler suite for the terminal. The roadmap treats both as deliverables of every phase, alongside the features they expose.

The nine panels

Each panel answers one question about a seed:

  • Overview orients, and PRNG shows the raw draw stream.
  • Type index renders the type system live, with dependency and reference graphs, so the roughly 160 interfaces stay navigable.
  • Structure viewer draws the expanded component tree in the shared observational prose.
  • Plausibility shows which rules passed and failed for a given expansion.
  • Material viewer shows each part's pick with the weights behind it.
  • Decoration inspector nests the layers per component.
  • Tag inspector shows the scored map with per-rule contributions, and rule calibration samples fire rates across settings; these two are where the measured-threshold work on the classification page actually happened.

The samplers

The CLI suite prints one pipeline stage each, for eyeballing output ahead of a panel landing, or for piping with --json:

deno task sample                  # gum menu over the samplers below
deno task sample:artefact         # anatomy tree + plausibility verdict
deno task sample:materials        # anatomy tree with each part's material pick
deno task sample:decoration       # decorative layers nested per part
deno task sample:features         # annotated classifier reading, per-value provenance
deno task sample:classification   # scored tag map with per-rule contributions

The features sampler carries per-value provenance: each extracted value names the component and policy that produced it, which is how collapse-policy behaviour (the dominant-blade and dominant-container decisions on the classification page) gets checked by hand. The samplers and the Explorer's structure viewer share the same prose renderer, so what the terminal says and what the panel says never drift.

Defects live in populations

Procgen defects are population properties, and a population is invisible without tooling. The wire-wrapping gate defect surfaced in a sampling pass; the elite inflation surfaced in fire-rate measurement; the fixture skew surfaced when a re-measurement disagreed with the original sample. None of them could have been seen in a unit test or a code review, because every individual artefact involved was fine. Determinism closes the loop: anything odd in a panel arrives with the seed that produced it, so every observation is a reproducible test case by construction.

What happens when the spec is wrong

Specs usually meet implementation in one of two ways: the spec quietly rots while the code moves on, or somebody rewrites it and the reasoning behind the first version disappears. This suite does a third thing. When implementation contradicts doc 05, the original text stays put, and a dated implementation note lands directly beneath it recording what shipped instead, why, and which task made the change.

A concrete run of it, from this year:

  1. Section 8.2 of doc 05 ends a paragraph with "you don't gild wood".
  2. Someone checks. Gilded wood over gesso is the commonest gilding in the historical record; the sentence is wrong, and so is the substrate test built on it.
  3. The sentence is removed. A note dated 2026-08-07 lands where it stood, saying what was wrong, citing the task (2GN.101) that re-gated the test on rigidity.
  4. Anyone who learned the old rule finds the correction exactly where their memory points; anyone arriving fresh reads the current rule and the fossil of the old one in the same screenful.
Why keep the wrong text nearby The cost is a longer document. What it buys: the note names the evidence and the reasoning, so a future reader can re-litigate the decision; the spec doubles as a decision log without a separate ADR system to maintain; and a contradiction between doc and code is always one of two known states (note pending, or defect) rather than the usual third state of "who knows which is current". The decoration depth table is the pattern at full stretch: it stays in the doc even though its two middle corners were proven unsatisfiable, with the note explaining the volume/grade split that shipped instead.

The register, the spikes, the ids

Three mechanisms keep fourteen documents from contradicting each other:

  • The propagation register (doc 12). Corrections ripple: a ruling that changes doc 05 usually obliges edits in other documents, and the register is the ledger that tracks each ripple from logged to applied. Sixteen entries had completed at the time of writing, none pending.
  • Design spikes get standalone write-ups in docs/spikes/ holding the full argument (measurements, alternatives rejected and why), while doc 11 holds only the ruling; the reasoning and the law live at different addresses, and each spike names where its ruling landed.
  • Stable task ids stitch it all to the code. A comment reading 2GN.84 resolves to the same task in the roadmap, the same doc 12 entry and the same spike, so provenance survives in all directions; several passages on these pages were written by following one id across all three.
